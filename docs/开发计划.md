# LLM API 负载均衡网关 — 开发计划

> 目标：把多厂商大模型 API 聚合成一个统一入口，定时体检剔除坏渠道，按优先级 + 权重做负载均衡，调用失败自动无感切换下一个。
> 参考项目：new-api（架构与后台 UX）、LiteLLM（多协议适配思想）、FreeRouter（实时健康探测 + 故障切换策略）。

---

## 0. 一期范围（MVP）与明确不做

**做：**
1. 渠道（Channel）管理：厂商类型、Base URL、API Key、模型列表、优先级、权重、启停
2. 定时健康检查：探测 → 连续失败自动停用 → 冷却 → 成功自动恢复
3. 统一网关：对外暴露 **OpenAI 兼容** `/v1/chat/completions`（含 SSE 流式）、`/v1/models`
4. 负载均衡：优先级分组 + 组内加权随机 / 轮询
5. 故障无感切换：可重试错误自动换渠道，对客户端透明
6. 模型路由表：用户为每个"对外模型名"指定优先用哪些渠道（顺序可调）
7. 对外网关 Key 管理 + 基础限流
8. 请求日志 + 用量统计看板
9. Web 管理后台（类 new-api，但砍掉冗余功能）

**一期不做：** 多用户/分组/充值/兑换码、OAuth/LDAP、绘图与音频、Midjourney、Redis、多节点分布式、Claude/Gemini 原生协议（仅通过 OpenAI 兼容层接入）。

## 1. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 后端 | **Node.js 22 + TypeScript + Fastify** | 本机已就绪（Go 未安装）；SSE 流式转发用 `stream.pipeline` 天然顺；单进程部署 |
| 数据库 | **SQLite（better-sqlite3）** | 用户指定；同步 API、零运维；WAL 模式 + 定期 VACUUM |
| ORM | Drizzle ORM（或 Kysely） | 轻量、类型安全、迁移文件可控；不用 Prisma（体积大、冷启慢） |
| 定时任务 | node-cron + 自研并发池 | 健康检查需要并发控制与超时，自研池比通用队列更可控 |
| HTTP 客户端 | undici（内置）+ 自封装 fetch | 原生支持流式响应体，无需额外依赖 |
| 前端 | **React 18 + Vite + Ant Design 5 + zustand + react-router + ECharts** | antd 表格/表单/Modal 开箱即用，页面观感直接对标 new-api |
| 构建部署 | 后端 esbuild 打包 + 前端 Vite 构建到 `dist`，Node 静态托管单端口 | `node dist/server.js` 一条命令启动，或 Docker 单镜像 |

**备选方案 B（需先装 Go 1.22+）：** Go + Gin + GORM + 前端同上。优势是性能天花板更高、更贴近 new-api 源码（可直接借鉴其 relay/adaptor 设计）、最终产物是单个二进制无依赖。若你愿意装 Go，我更推荐 B。

## 4. 核心模块设计

### 4.1 渠道选择与负载均衡
```
请求 public_model
  → 查 model_routes 得到有序 channel_ids
  → 过滤：enabled && status != disabled && !in_cooldown
  → 按 strategy 排序/加权：
       priority     : 按数组顺序取第一个可用的（严格优先级组）
       weighted     : 组内按 weight 加权随机
       round_robin  : 组内轮询
  → 得到候选队列（而非单个），供失败重试时依次取用
```
用户"优先用哪些模型"的诉求，落在 **model_routes.channel_ids 的顺序** 上，UI 用可拖拽列表直接调序。

### 4.2 健康检查调度
- cron 间隔可配（默认 5 分钟），并发池（默认 20）
- 探测方式二选一（设置项）：
  - **轻量探测**：`GET /v1/models`，快、不花钱，但探不出额度耗尽
  - **真实探测**：`POST /v1/chat/completions` 发 1 条极短消息 `max_tokens:1`，准确但消耗极少量 token
- 判定：连续失败 ≥ `fail_threshold` → `status=failing` 且自动 `enabled=0`，写入 `cooldown_until`（指数退避：5min → 10min → 30min，上限可配）
- 恢复：冷却期过后重新探测，连续成功 ≥ `recover_threshold` → 自动恢复启用
- 手动"立即测试"和"强制启用"永远可用

### 4.3 故障无感切换（最关键的一块）
错误分类：
- **可重试（自动切换下一渠道）**：连接错误、超时、429、500/502/503/504、上游返回空 body
- **不可重试（直接返回客户端）**：400 参数错误、401 鉴权失败、403 无权限、404 模型不存在
- **特殊**：401/403 说明渠道 Key 失效 → 立即标记 `failing` 并停用（不必等定时器）

流式（SSE）关键点：
- **首字节之前失败** → 完全透明：换渠道重发，客户端无感知
- **首字节之后失败** → **不能静默切换**（会导致输出重复/内容损坏）；改为：单条请求内不重试，直接结束流并返回错误事件，同时标记渠道失败。客户端重试时由网关重新选路。
- 每次切换记录到 `failover_chain`，日志页可看到完整链路

### 4.4 Adaptor 抽象
```ts
interface Adaptor {
  buildRequest(ctx): { url, headers, body }
  parseStream(chunk): ParsedChunk[]
  parseResponse(body): NormalizedResponse
  extractUsage(res): { promptTokens, completionTokens }
  isRetryableError(status, body): boolean
}
```
一期只实现 `openai.ts`（覆盖 DeepSeek / 通义 / 豆包 / 硅基流动 / Groq / OpenRouter / vLLM / Ollama / 本地 llama.cpp 等绝大多数），接口预留，二期加 `anthropic.ts`、`gemini.ts`。

### 4.5 安全
- 上游 API Key 落库 AES-256-GCM 加密，密钥从环境变量 `MASTER_KEY` 派生；列表接口只返回掩码 `sk-***abcd`
- 对外网关 Key 只存 SHA-256 哈希 + 前缀
- 后台 JWT，默认强制修改初始密码

## 7. 主要风险与对策

| 风险 | 对策 |
|---|---|
| SQLite 并发写压力 | WAL 模式；日志写入走内存队列批量落盘；高频计数用内存累加 + 定时落库 |
| 流式响应中途失败 | 明确策略：首字节前透明重试，首字节后不静默切换，返回标准错误事件 |
| 健康检查把免费额度跑光 | 默认用 `/v1/models` 轻量探测；真实探测仅对标记为"需真实探测"的渠道开启 |
| Token 统计不准（部分厂商不返回 usage） | 上游无 usage 时用 tiktoken 近似估算，日志里标注估算标记 |
| 上游返回格式微差异 | adaptor 层做容错解析，未知字段忽略，缺字段补默认 |

## 8. 已确认决策（2026-09-04）

| 项 | 结论 |
|---|---|
| 技术栈 | ✅ **Node.js 22 + TypeScript + Fastify + Drizzle + better-sqlite3**（本机已装 Node，无需额外环境） |
| 协议范围 | ✅ **一期只做 OpenAI 兼容适配器**，Adaptor 接口预留，二期再扩 Claude / Gemini 原生 |
| 使用形态 | ✅ **纯自用单机**：单管理员、无计费/充值/分组；网关 Key 仅用于区分调用方 + 限流 + 用量归属 |

对应简化：删除 `admins` 多用户与分组/额度相关设计；`gateway_keys` 退化为"访问令牌"表（保留 allowed_models / rpm_limit / enabled / expires_at）。

## 9. 补充可选项（你说要就加）
- 上游 Key 池：同一渠道配多个 Key 轮询（防单 Key 限流）
- 模型别名映射：`gpt-4o` → 上游 `deepseek-v3`
- 自动发现：调用 `/v1/models` 自动填充渠道模型列表
- 延迟优先策略：按最近探测延迟排序而非固定优先级
- 渠道标签/分组：按用途（长文本 / 代码 / 廉价）分组路由
